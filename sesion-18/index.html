El principio de divide y vencerás.

Es la estrategia más vieja del oficio: ningún problema grande se resuelve de un golpe. Se parte en problemas pequeños, cada uno fácil de entender y de probar. En programación, cada pedazo se llama función.

Imagina un programa de cajero automático escrito de corrido: ochenta líneas que validan el PIN, consultan el saldo, retiran dinero, depositan, imprimen el recibo… todo amontonado en un solo bloque. Funciona. Pero si mañana cambia la regla del retiro, tienes que leer las ochenta líneas para encontrar dónde tocar. Y si te equivocas, rompes algo que no tenía nada que ver.

Ahora imagina el mismo programa partido en cinco funciones: validar_pin, consultar_saldo, retirar, depositar e imprimir_recibo. Cada una hace una sola cosa, cabe en la pantalla y se lee como una frase. Cambiar la regla del retiro es ahora abrir una sola función y arreglarla ahí. Lo demás ni se entera.

La gran idea: una función es un nombre que le pones a un trozo de trabajo. En vez de repetir o amontonar código, lo encierras, lo bautizas y lo llamas cuando lo necesitas.
antes · todo amontonado

Un solo muro de 80 líneas. Para entender qué hace el retiro, hay que leerlo todo. Si copias y pegas el mismo cálculo tres veces, tienes tres lugares que mantener.

# 80 líneas seguidas # ...validar... saldo... # ...retirar... recibo... # todo en main, sin nombres
después · modular

Cinco funciones

Cada tarea tiene su nombre y su lugar. El programa principal se vuelve un índice legible que solo llama funciones. Cada pieza se prueba por separado.

validar_pin() consultar_saldo() retirar() imprimir_recibo()

Mismo resultado en pantalla, distinta arquitectura por dentro. El monolito y los módulos hacen lo mismo hoy; pero solo uno seguirá vivo y editable dentro de seis meses.

i.

Anatomía de una función.

Toda función en Python tiene la misma forma. Conócela una vez y las reconocerás todas. Estas son las cinco partes que importan: la palabra clave, el nombre, el parámetro, el cuerpo y la devolución.

ANATOMÍA · def
def area_circulo(radio):
      return 3.1416 * radio * radio
def
La palabra clave que anuncia: «aquí defino una función».
area_circulo
El nombre. Un verbo o sustantivo claro, en snake_case.
(radio)
El parámetro: el dato que la función recibe para trabajar.
return
Devuelve el resultado a quien la llamó. La función entrega su fruto.
3.1416 * …
El cuerpo: el trabajo en sí, siempre sangrado 4 espacios.

Definir una función no la ejecuta: solo le enseña a Python cómo hacer algo y lo guarda con un nombre. Para que trabaje, hay que llamarla por su nombre y pasarle el argumento entre paréntesis. Entonces el dato entra por el parámetro, el cuerpo corre, y return entrega el resultado de vuelta.

Definir · enseñar la receta

definir.py
# PASO 1 · definimos la función
# (esto NO la ejecuta todavía)
def area_circulo(radio):
    # recibe el radio, devuelve el área
    return 3.1416 * radio * radio

Llamar · usar la receta

llamar.py
# PASO 2 · la llamamos con un argumento
chico = area_circulo(2)
grande = area_circulo(10)

print(chico)   # 12.5664
print(grande)  # 314.16
Una función, escrita una vez; usada muchas. No reescribimos la fórmula del área dos veces: la definimos una sola vez y la llamamos con distintos radios. Eso es reutilización, el premio de modularizar.
ii.

El gran malentendido: print() no es return.

Es la confusión número uno de quien empieza con funciones. Las dos hacen «que algo salga» de la función, pero son cosas distintas. Una le habla al humano; la otra le habla al programa.

print() · le habla al humano

Muestra un texto en la pantalla y se acabó. Es para que tú lo leas. El programa no se queda con nada: lo dicho, dicho está. Si intentas guardar lo que «devuelve», recibes un None vacío.

# sirve para AVISAR, no para calcular

return · le habla al programa

Entrega un valor de vuelta a quien llamó la función. Ese valor se puede guardar en una variable, sumar, comparar o pasar a otra función. Es la materia prima con la que el programa sigue trabajando.

# sirve para CALCULAR y seguir usando
print_vs_return.py
# ──────── Versión que solo IMPRIME ────────
def cuadrado_imprime(numero):
    print(numero * numero)   # muestra en pantalla y nada más

resultado = cuadrado_imprime(5)   # imprime: 25
print(resultado)                  # imprime: None  ← no guardó nada
# total = resultado + 1  →  TypeError: no se puede sumar None


# ──────── Versión que DEVUELVE ────────
def cuadrado(numero):
    return numero * numero    # entrega el valor a quien llamó

resultado = cuadrado(5)            # resultado vale 25 de verdad
total = resultado + 1             # ¡ahora sí podemos seguir calculando!
print(total)                     # imprime: 26
Regla práctica: si necesitas usar el resultado más adelante, usa return. Reserva print() para el último momento, cuando ya solo quieres mostrarle algo a la persona. Una función bien hecha calcula con return y deja que otra parte del programa decida si imprimir.
iii.

Una función, una responsabilidad.

La regla de oro del diseño modular. Si para explicar qué hace tu función tienes que usar la palabra «y», probablemente son dos funciones disfrazadas de una. Pártela.

1

Hace una sola cosa

«Calcula el promedio.» No «calcula el promedio y lo imprime y lo guarda». Una tarea por función.

2

Su nombre lo dice todo

Un verbo claro: validar_pin, calcular_iva. Si lees el nombre y ya sabes qué hace, está bien bautizada.

3

Cabe en la pantalla

Si necesitas hacer scroll para verla completa, es demasiado larga. Pártela en funciones más pequeñas que se llamen entre sí.

una_responsabilidad.py
# ✗ MAL: una función que hace de todo
def procesar(nota):
    if nota >= 60:           # decide
        estado = "APROBADO"
    else:
        estado = "REPROBADO"
    print("Resultado: " + estado)  # y además imprime
    # hace dos cosas: decidir Y mostrar


# ✓ BIEN: cada función, una sola tarea
def esta_aprobado(nota):
    # responsabilidad única: DECIDIR
    return nota >= 60

def mostrar_resultado(aprobado):
    # responsabilidad única: MOSTRAR
    if aprobado:
        print("Resultado: APROBADO")
    else:
        print("Resultado: REPROBADO")

# el programa principal solo coordina:
mostrar_resultado(esta_aprobado(75))   # Resultado: APROBADO
Fíjate en la última línea: esta_aprobado(75) devuelve True, y ese valor entra directo a mostrar_resultado. Las funciones pequeñas encajan unas en otras como piezas. Eso es modularidad de verdad.
iv.

Live coding: descomponer el cajero ATM.

Recuperamos el cajero de sesiones pasadas —ese muro de código que crecía sin control— y lo refactorizamos en clase, en vivo, función por función. No le cambiamos lo que hace: le cambiamos la forma en que está escrito. Eso es refactorizar.

Primero acordamos juntos el mapa de funciones: qué tareas hay dentro del cajero, qué nombre le ponemos a cada una, qué dato recibe y qué devuelve. Una vez que el mapa está claro, escribir cada función es casi mecánico. El diseño es el trabajo difícil; el código es la consecuencia.

atm_funciones.py
# Cada función vive sola y se prueba sola.
PIN_CORRECTO = 1234          # constante (como en la sesión 6)

def validar_pin(pin):
    # DECIDE: ¿el PIN es correcto? devuelve True o False
    return pin == PIN_CORRECTO

def retirar(saldo, monto):
    # CALCULA y devuelve el saldo nuevo
    if monto > saldo:
        print("Fondos insuficientes.")  # avisa al usuario
        return saldo            # y deja el saldo sin cambios
    return saldo - monto

def depositar(saldo, monto):
    return saldo + monto

# El programa principal solo COORDINA las piezas:
saldo = 1500.0
if validar_pin(1234):
    saldo = retirar(saldo, 500.0)
    saldo = depositar(saldo, 200.0)
    print("Saldo final:", saldo)   # Saldo final: 1200.0

Refactoriza el cajero

Toma la versión vieja del cajero (el bloque monolítico) y pártela en funciones bien nombradas, sin cambiar lo que el programa hace para el usuario. Cuando termines, el main debe leerse como un índice de tareas, no como un muro.

  • Al menos 4 funciones con una sola responsabilidad cada una
  • Usa return para calcular; reserva print() para mostrar
  • Nombres en snake_case que digan qué hace cada función
  • El saldo inicial vive en una constante
  • Comenta cada función con su responsabilidad en una línea
