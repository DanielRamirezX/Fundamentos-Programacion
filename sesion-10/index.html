i.

El acuerdo: PEP 8.

PEP 8 es la guía de estilo oficial de Python: un acuerdo entre millones de programadores sobre cómo escribir código que cualquiera pueda leer. No cambia lo que el programa hace; cambia quién lo puede entender.

Tu código corre igual con o sin estilo. Pero el código se escribe una vez y se lee decenas de veces —por tu yo de la próxima semana, por tu equipo, por quien te evalúa. PEP 8 elimina las discusiones tontas (¿una o dos líneas en blanco?) para que pienses en lo que importa.

  • Nombres: snake_case para variables y funciones; MAYÚSCULAS para constantes —como ya haces desde la sesión 06.
  • Espacios: uno alrededor de los operadores (a = b + 1), ninguno pegado a los paréntesis.
  • Indentación: 4 espacios, nunca tabuladores mezclados.
  • Longitud de línea: hasta 79 caracteres; si se alarga, parte la línea.
Regla del cuaderno: escribe el código pensando en quien lo va a leer mañana sin contexto. Ese «alguien» casi siempre eres tú.
estilo.py
# ✗ Funciona, pero pelea con el lector
def CalcularTotal(p,iva):
  Resultado=p+p*iva
  return Resultado

t=CalcularTotal(100,0.16)


# ✓ El mismo cálculo, ahora legible (PEP 8)
IVA = 0.16


def calcular_total(precio, iva):
    total = precio + precio * iva
    return total


total = calcular_total(100, IVA)

Nombres con sentido

Variables y funciones en snake_case; constantes en MAYÚSCULAS. Que el nombre diga qué guarda, no x ni dato2.

x = 18 ✗
edad_minima = 18 ✓

Espacios que respiran

Un espacio alrededor de =, +, ==; coma seguida de espacio. Nada pegado a los paréntesis.

total=a+b*c ✗
total = a + b * c ✓

Indentación pareja

Siempre 4 espacios. Nunca mezcles tabuladores y espacios: Python truena con un TabError o, peor, miente sin avisar.

if ok:
  hacer()   # 2 espacios ✗
if ok:
    hacer()  # 4 espacios ✓

Líneas cortas

Hasta 79 caracteres. Si una condición se alarga, pártela con paréntesis y léela en dos renglones.

if a and b and c and d and e and f: ✗
if (a and b and c
        and d and e): ✓
ii.

Comentar el por qué, no el qué.

El código ya dice qué hace —se lee solo. Un buen comentario explica lo que el código no puede: el por qué, la decisión, la trampa que evitaste. Comentar lo obvio es ruido que envejece mal.

✗ comentario inútil · narra el «qué»

Repite lo que ya se ve

Este comentario no aporta nada: el código ya grita lo que hace. Y si cambias el código y olvidas el comentario, ahora miente.

# sumar 1 a contador
contador = contador + 1

# revisar si edad es mayor a 18
if edad > 18:
    ...
✓ comentario valioso · explica el «por qué»

Cuenta lo que el código calla

Aquí el comentario revela una decisión y una regla del negocio que ningún lector adivinaría leyendo solo las líneas.

# 18 inclusive: la mayoría de edad
# legal en México cuenta el día 18.
if edad >= 18:
    ...

iii.

El debugger: ver, no adivinar.

Depurar a punta de print() es adivinar a oscuras. El debugger de VS Code detiene el programa donde tú quieras y te deja mirar dentro: ver cada variable, avanzar línea por línea y seguir la pista del error sin tocar el código.

Un breakpoint es un alto: pones un punto rojo a la izquierda de una línea y el programa se congela justo antes de ejecutarla. Ahí abres el panel de variables y ves la verdad —no lo que crees que vale promedio, sino lo que realmente vale.

Recuerda el bug lógico de la sesión 05: el programa corría, pero el promedio salía mal. Sin debugger, lo persigues a ciegas. Con él, pones un alto, miras suma y total en cada vuelta, y el error se delata solo.

Regla del cuaderno: antes de cambiar una sola línea para «arreglar» un bug, ponlo bajo el debugger y obsérvalo. La mitad de los bugs no son lo que crees que son.
promedio.py
def promedio(calificaciones):
    suma = 0
    total = len(calificaciones)
    for calif in calificaciones:
        suma = suma + calif
    return suma / total


notas = [8.0, 9.5, 7.0]
print(promedio(notas))
>>> 8.166666666666666

iv.

La IA como copiloto, no como piloto.

La inteligencia artificial puede acelerarte —o impedir que aprendas. La diferencia no está en la herramienta, sino en cómo la usas. La regla del curso es simple: pide explicaciones, no soluciones; y nunca firmes código que no entiendes.

Sí: úsala para entender

La IA como tutor que te explica, no como mano que te resuelve.

  • «Explícame qué hace este for línea por línea.»
  • «¿Por qué me sale este TypeError y qué lo causa?»
  • «Dame tres pistas para encontrar el bug, sin decirme la solución.»
  • «¿Mi nombre de variable sigue PEP 8? Sugiéreme uno mejor.»
  • «¿Qué conceptos debo estudiar para resolver esto yo solo?»

No: que piense por ti

Si copias lo que no entiendes, el examen —y la vida— te lo cobrará.

  • «Hazme toda la práctica del cajero y dámela lista.»
  • Pegar código generado sin leerlo ni probarlo.
  • Entregar como tuyo algo que no podrías explicar en el pizarrón.
  • Confiar ciegamente: la IA también se equivoca y alucina.
  • Saltarte el debugger porque «la IA ya me lo arregló».
▶ EL MISMO PROBLEMA, DOS FORMAS DE PEDIR
PILOTO «Mi promedio sale mal, arréglame el código y pégamelo completo.» — Te quedas igual de ignorante; no aprendiste nada y no sabrás defenderlo.
COPILOTO «Mi promedio sale mal. No me des la solución: dime qué variables debería vigilar en el debugger y qué tipo de error suele causar esto.» — Aprendes a cazarlo tú.
v.

El linter: un PEP 8 que no se cansa.

Un linter es un programa que revisa tu programa: lee tu código y te marca, en tiempo real, dónde rompes el estilo o dejas un error tonto. ruff y flake8 son los más usados; viven dentro de VS Code y trabajan mientras escribes.

El linter no juzga si tu lógica es correcta —para eso está el debugger—; juzga si tu código es limpio. Subraya la variable sin usar, el espacio de más, la línea de 120 caracteres. Es PEP 8 convertido en un asistente incansable que nunca se distrae.

Instalas la extensión Ruff de VS Code y, a partir de ahí, los problemas aparecen subrayados como faltas de ortografía. También puedes correrlo en la terminal para una revisión completa antes de entregar.

  • Instala en clase: pip install ruff
  • Revisa un archivo: ruff check estilo.py
  • Arregla lo automático: ruff check --fix estilo.py
Ojo: el linter te dice cómo escribir mejor, no qué escribir. Sigue siendo tu cabeza la que programa.

La cacería a mano.

Dos actividades en clase. Primero auditamos en grupo un programa mal escrito; después cada quien caza un bug sin IA, usando solo el debugger. Hoy demuestras que sabes pensar, no solo preguntar.

Actividad 1 · en grupo

Auditoría de estilo

Proyectamos un programa feo pero funcional y, entre todos, lo refactorizamos: cazamos cada violación a PEP 8 y la corregimos en vivo. Mismo comportamiento, mucho mejor código.

  • Encuentra los nombres que no son snake_case
  • Marca los espacios faltantes alrededor de operadores
  • Detecta las líneas que pasan de 79 caracteres
  • Convierte los números mágicos en constantes con nombre
  • Borra los comentarios que solo repiten el «qué»
por_auditar.py
# el codigo a mejorar en el pizarron
def Calc( N1,N2 ):
  R=N1*0.16+N2 # sumar
  return R

x=Calc(100,50)
print("resultado",x)
Actividad 2 · individual · sin IA

Caza el bug con el debugger

Te entrego un programa que corre sin reventar pero da un resultado falso —un bug lógico, de los que no avisan. Tu reto: encontrarlo usando solo el debugger. Nada de IA, nada de print() regados.

  • Pon un breakpoint antes del cálculo sospechoso
  • Avanza con F10 y mira las variables en cada vuelta
  • Compara lo que crees que vale cada una con lo que realmente vale
  • Anota en qué línea la realidad se separó de tu suposición
  • Arréglalo y vuelve a correr bajo el debugger para confirmar
bug_logico.py
# Promedio de aprobados (>= 6)
def promedio_aprobados(notas):
    suma = 0
    cuenta = 0
    for nota in notas:
        if nota >= 6:
            suma = suma + nota
        cuenta = cuenta + 1
    return suma / cuenta


print(promedio_aprobados([9, 4, 8]))
>>> 5.666...  # ¿no debería ser 8.5?

Media página, en tus palabras: ¿cómo usas la IA en esta materia de forma responsable? Da un ejemplo de algo que le preguntaste para aprender, no para que te lo resolviera.

4. Commit honesto

Sube todo a GitHub con un mensaje claro: "sesion-10: refactor + carta de IA". Sin «final», sin «v2». Tu repositorio es tu palabra.

tip: $ git commit -m "sesion-10: ..."

Criterios de evaluación

  1. Sin errores de sintaxis ni de ejecución — el programa refactorizado corre igual que el original.
  2. Lógica correcta — el refactor no rompió nada: hace exactamente lo mismo que antes.
  3. Funcionamiento óptimo — cumple PEP 8 y pasa ruff check sin advertencias; comentarios que explican el «por qué».
  4. Autenticidad — código y carta escritos por ti; la IA, si la usaste, queda declarada con honestidad.

Evidencia a entregar

.md README.md — tres mejoras explicadas y la captura del linter en verde.
.md uso_de_ia.md — media página sobre tu uso responsable de la IA, con un ejemplo real.
