Cuando todo falla.

La clase pasada tejimos laberintos con ciclos anidados: máquinas que repiten, combinan y llenan tablas sin equivocarse… mientras nadie las moleste. Pero el mundo real está lleno de dedos torpes y de gente con prisa. Hoy aceptamos una verdad incómoda: todo lo que puede fallar, tarde o temprano fallará. Un programa adulto no reza para que nada salga mal — se prepara para cuando salga. Aprendemos a atrapar el error en el aire, con try / except / else / finally, antes de que estrelle nuestro programa contra el suelo.

0

El usuario escribe «abc».

Empecemos por el accidente. Tu programa pide un número con int(input(...)) y el usuario, distraído, teclea texto. ¿Qué pasa? Mira las dos terminales: la misma entrada, dos destinos.

SIN protección — truena
¿Cuántos años tienes? abc
Traceback (most recent call last):
  File "edad.py", line 1, in <module>
ValueError: invalid literal for
int() with base 10: 'abc' El programa muere. El usuario ve un muro rojo que no entiende.
CON try/except — sobrevive
¿Cuántos años tienes? abc
Eso no parece un número. Inténtalo de nuevo.
¿Cuántos años tienes? 21
¡Perfecto, 21 años registrados! El programa entiende, perdona y continúa. Eso es robustez.

La diferencia no es magia. Es una red de seguridad de cuatro palabras. Le dices a Python: «intenta esto; si truena, no te mueras, ven aquí y manéjalo».

Una excepción es Python avisándote, en pleno vuelo, que algo se rompió: «no puedo convertir 'abc' a entero». Sin red, ese aviso detona y derriba el programa. Con try/except, lo atrapas y decides tú qué hacer.

No confundas: validar es revisar antes; manejar excepciones es estar listo para cuando, aún revisando, algo falle. Las dos juntas hacen un programa de verdad robusto.
red_de_seguridad.py
# Sin red: una entrada mala lo derriba
edad = int(input("¿Cuántos años? "))

# Con red: lo intenta y, si falla, responde
try:
    edad = int(input("¿Cuántos años? "))
except ValueError:
    print("Eso no parece un número.")
else:
    print(f"¡Perfecto, {edad} años!")
i.

La anatomía del bloque.

Son cuatro palabras clave, y cada una tiene su momento exacto. Dos son obligatorias para empezar (try y except); las otras dos refinan tu red.

try:

El terreno minado

Aquí va el código que podría fallar: la conversión, la división, el acceso al diccionario. Python lo ejecuta con la guardia en alto.

obligatorio
except:

El plan B

Si algo explotó, Python salta aquí en vez de morir. Atrapas el error por su nombre y respondes con cortesía.

obligatorio
else:

Si todo salió bien

Se ejecuta solo si el try no tronó. Útil para separar «lo que arriesga» de «lo que celebra».

opcional
finally:

Pase lo que pase

Se ejecuta siempre, con error o sin él. Para cerrar archivos, soltar recursos, despedir al usuario.

opcional
anatomia.py
def pedir_division():
    try:
        a = int(input("Dividendo: "))      # puede lanzar ValueError
        b = int(input("Divisor: "))
        resultado = a / b                  # puede lanzar ZeroDivisionError
    except ValueError:
        print("Escribe números enteros, por favor.")
    except ZeroDivisionError:
        print("No se puede dividir entre cero.")
    else:
        print(f"El resultado es {resultado}")    # solo si NO hubo error
    finally:
        print("— operación finalizada —")        # SIEMPRE se imprime


pedir_division()
# Entrada 8 y 2  ->  "El resultado es 4.0" + "— operación finalizada —"
# Entrada 8 y 0  ->  "No se puede dividir entre cero." + "— operación finalizada —"
# Entrada "x"    ->  "Escribe números enteros..." + "— operación finalizada —"
ii.

Los cuatro sospechosos.

No atrapes «cualquier error» a ciegas: eso esconde bugs reales. Atrapa el error que esperas, por su nombre. Estos cuatro son los que más visitarán tu cajero.

Excepción
Qué la provoca
En el cajero…
ValueError
Convertir texto que no es número: int("abc"), float("$5").
Teclean «mil» donde pides el monto.
ZeroDivisionError
Dividir entre cero: monto / personas con personas = 0.
Repartir un monto entre 0 personas.
KeyError
Pedir una llave que no existe en un diccionario: cuentas["9999"].
Consultar una cuenta inexistente.
FileNotFoundError
Abrir un archivo que no está: open("bitacora.txt").
Leer un registro que aún no se creó.
sospechosos.py
# Cada error tiene su propio except, con su propio mensaje
cuentas = {"1001": 2500.0, "1002": 800.0}

try:
    numero = input("Cuenta: ")
    saldo  = cuentas[numero]              # KeyError si no existe
    monto  = float(input("Retiro: $"))    # ValueError si es texto
    veces  = int(input("Mensualidades: "))
    cuota  = monto / veces                # ZeroDivisionError si veces es 0
except KeyError:
    print("Esa cuenta no existe.")
except ValueError:
    print("El monto debe ser un número.")
except ZeroDivisionError:
    print("El número de mensualidades no puede ser cero.")
else:
    print(f"Cuota mensual: ${cuota:.2f}")
cuándo CAPTURAR

Atrápala si puedes responder

  • El error viene de afuera: entrada del usuario, un archivo, la red. Cosas que no controlas.
  • Tienes un plan B útil: pedir el dato otra vez, usar un valor por defecto, avisar con calma.
  • Quieres que el programa siga vivo pase lo que pase: un cajero, un servidor, un juego.
cuándo DEJAR PROPAGAR

Déjala subir si no puedes arreglarla

  • El error revela un bug tuyo: una variable mal escrita, lógica rota. Ocultarlo es peor.
  • No tienes una respuesta honesta: capturar «todo» con un except: pelón silencia problemas serios.
  • En un script pequeño, a veces el traceback es la mejor pista para ti, el programador. Que truene… en tu máquina.

Cómo viene marcado el archivo

Abre el archivo y busca cada comentario # FRÁGIL: ahí vive un punto que hoy revienta el programa. Junto a él, un # PASO te dice exactamente qué endurecer.

No borres las marcas. Lee el peligro, envuelve la línea con tu red try/except y vuelve a correr probando justo la entrada que antes lo rompía.

El plano te señala la grieta; tú decides cómo sellarla.

Criterios de evaluación

  1. Sin errores de sintaxis ni de ejecución — el cajero corre completo y no muestra un solo traceback ante ninguna de las entradas malas.
  2. Lógica correcta — cada except atrapa el error correcto y por su nombre; nada de except: pelón que silencie todo.
  3. Funcionamiento óptimo — los seis puntos frágiles endurecidos, validación de saldo y monto, opción de menú inexistente manejada con cortesía.
  4. Autenticidad — código tuyo, no copiado; con tag de versión v2.0 en tu repositorio.
